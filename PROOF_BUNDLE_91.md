## Scaling & Densifying Finite Certificates

The biggest near-term win is not a single new witness, but a denser certificate
base with repeated structure checks.

Current anchor points:

- n=14: strict per-n witness certificate with the strongest invariant package.
- n=26: strict per-n witness certificate with a distinct seed-family mixture.
- n=32: bounded exclusion slice plus consensus plateau at exact best = 484.

What the new pattern ledger adds:

- it compares all available witness bundles side by side,
- it separates common structure from n-specific variation,
- it identifies the consensus plateau that can anchor an inductive bridge,
- it exposes the observed seed families that should be tracked in future searches.

Next densification target:

1. Add more certified n values around the current anchors, especially nearby even n.
2. Require at least two independent minimizers per new n when the search can support it.
3. Attach a stability certificate to each new witness bundle so local perturbations are tracked explicitly.
4. Re-run the pattern ledger after every new batch and update the conjectures it emits.

The practical criterion for advancement is simple: each new bundle should either
advance a rung or widen the verified base enough to make the rung-3 pattern
ledger sharper.

## Stability Certificates

The current witness certificates are pointwise non-similarity proofs. The next
finite-to-asymptotic improvement is to attach a local stability certificate to
each witness family.

Required shape of that certificate:

1. A normalized neighborhood description around each witness branch.
2. An interval lower bound showing perturbations cannot reduce the exact
   objective below the certified minimum.
3. A similarity-separation bound showing no nearby perturbation merges the two
   known branches up to similarity.

The new pattern ledger is the bridge artifact: it identifies the recurring seed
families and the consensus plateau that those stability certificates would have
to preserve.

## Main Claim

There is verified computational evidence, with strict replayable checks, that
the repository can certify both of the following:

1. For selected hard values of n, witness pairs are provably non-similar under
   the repository’s invariant checks.
2. For n = 32, the explored certified database rows admit a nontrivial bounded
   exclusion log with a strict gap above the best exact objective.

This is the strongest current proof bundle because it combines exact objective
certification, invariant-based non-similarity, and bounded exclusion in a form
that is machine-checkable.

## Theorem 1: Certified Non-Similarity at Selected n

For n = 14, n = 22, and n = 26, the repository contains witness certificates that pass
strict verification and certify non-similarity via multiple similarity
invariants.

More precisely, the witness JSON proof objects stored at
[results/erdos91_witness_n14_formal_upgrade_v2.json](results/erdos91_witness_n14_formal_upgrade_v2.json)
[results/erdos91_witness_n22.json](results/erdos91_witness_n22.json)
and
[results/erdos91_witness_n26_formal_upgrade.json](results/erdos91_witness_n26_formal_upgrade.json)
encode the following checks:

- equal exact objective value for the witness pair,
- mismatch of normalized squared-distance spectra,
- mismatch of normalized squared doubled-area spectra,
- mismatch of centered Gram eigenvalue ratio spectra,
- certified lower bounds for the mismatch certificates,
- strict verifier replay under [verify_witness_proof_object.py](verify_witness_proof_object.py).

### Proof Sketch

Let P and Q be the two candidate configurations in a witness certificate.
The verifier recomputes the normalized similarity invariants from the stored
point sets and checks that at least one invariant differs. Because any
Euclidean similarity preserves all three invariant families, mismatch implies
P is not similar to Q.

The strengthened proof objects do not rely on a single heuristic signal.
They require agreement across exact objective data and several independent
invariant families, which makes the non-similarity conclusion robust against a
single feature-level failure.

## Theorem 2: Bounded Exclusion at n = 32

The fixed-n exclusion report at
[results/erdos91_exclusion_n32_v1.md](results/erdos91_exclusion_n32_v1.md)
records a nontrivial bounded exclusion slice over the certified database rows
in scope.

The report certifies the following fixed-n facts:

- certified minimizers in scope: 62,
- exact-valid rows with larger exact objective: 456,
- next-best exact distinct squared-distance count: 485,
- exact objective gap to next-best: 1.

### Proof Sketch

The exclusion generator loads the fixed-n database rows, separates exact-valid
rows from uncertified rows, identifies the best exact objective among the
certified rows in scope, and then records every exact-valid row whose objective
is strictly larger than that best value.

This produces a bounded pruning log, not a global completeness proof. The value
of the artifact is that it cleanly splits certified minimizers, excluded
certified candidates, and uncertified search noise.

## Combined Conclusion

Taken together, these artifacts establish the best proof bundle currently
available in the repository:

- exact objective certification for selected n,
- strict invariant-based non-similarity certificates for selected witness pairs,
- the newly promoted n=22 witness that widens the finite core,
- bounded exclusion over a larger fixed-n search slice,
- replayable verification of the proof objects.

That is the strongest auditable statement presently supported by the codebase.
It is still not the full asymptotic theorem for all sufficiently large n.

## Remaining Gap

The open gap is the one highlighted in [PROOF_PROGRAM_91.md](PROOF_PROGRAM_91.md):
global completeness over configuration space and an asymptotic lift from the
verified per-n bundles to all n >= N.

The next proof-grade step is cell-level branch-and-bound exclusion with interval
lower bounds, followed by a branch-continuation lemma across n.

the manifest whenever new witness files, exclusion runs, or conjecture outputs
land in the repository.

The lightweight update flow is:

1. Update the manifest when a rung changes state.
2. Regenerate [ladder_status.md](ladder_status.md) from the manifest.
3. Run the pattern ledger generator to refresh structural conjectures.
4. Attach the updated bundle to the next proof milestone.
